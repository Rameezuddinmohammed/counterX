## 1. What's actually done (verified by real execution, not static reading)

**Phase 3 — remote MCP connector.** Buyers can now (once someone completes step 4 below) connect Claude.ai directly to a hosted `https://counter-remote-mcp.fly.dev` URL instead of running a local stdio process.

1. **Key-custody spike**: confirmed by running a real local Vault 1.17.6 dev server that its Transit engine signs with a non-exportable Ed25519 key, and the signature verifies bit-for-bit with this repo's own `@noble/ed25519`. Chose Vault over AWS/GCP KMS (no AWS/GCP credentials exist anywhere in this environment; ADR-0006's AWS default inherits from ADR-0009's AWS pilot target, which was never actually realized — the real deployment is Fly + Supabase, a stale-doc-vs-code conflict flagged, not silently resolved).
2. **`VaultSecureKeyStore`** (`packages/wallet-domain`) + **`PostgresVaultKeyRepository`** (`packages/data`, migration `0023`): multi-tenant Ed25519 signing where a store built for tenant A structurally cannot reach tenant B's key (every keyId is checked against a durable ownership record before Vault is ever called).
3. **`apps/remote-mcp`**: Streamable-HTTP MCP server fronted by `CounterOAuthServerProvider`, a genuine **two-legged OAuth 2.1 proxy** — necessary because MCP clients require dynamic client registration and Auth0 doesn't support it. Full design in the file's own header comment. The MCP SDK's stock `ProxyOAuthServerProvider` does NOT work for this (confirmed by reading its source — it only supports a single fixed downstream client). Migration `0024` (`platform.remote_mcp_clients`) is the durable DCR registry.
4. **Automatic Vault token rotation**: `apps/remote-mcp`'s Vault credential is a genuine Vault **periodic token** (30-day window), renewed by the app itself every 6 hours (`src/vault-token-renewal.ts`) — not a long fixed TTL, which isn't real rotation.
5. **Real bug found and fixed in shared code**: `packages/http-api-kit`'s `authPlugin` skip-route matching ignored query strings, silently 401ing any OAuth route (`/authorize?client_id=...`). Was latent everywhere else; `apps/remote-mcp` was the first thing to actually hit it.
6. **Two more real bugs found only by running the deployed system**, both documented in `vault-config.hcl`: Vault's listener was IPv4-only (`0.0.0.0`) and unreachable over Fly's IPv6-only private network — every local ssh-console health check kept passing while cross-app calls silently failed; and the `remote-mcp-signer` Vault policy had no grant for `auth/token/renew-self`, so automatic renewal 403'd until fixed.
7. **Real bug found by an actual Claude.ai Connector attempt (PR #28)**: `/mcp`'s 401 carried no `WWW-Authenticate: Bearer resource_metadata="..."` header, so a connecting client's auto-discovery flow had nothing to follow and fell back to "Couldn't determine the server settings — configure manually." Fixed in `packages/http-api-kit/src/auth.ts` (`resourceMetadataUrl` option, RFC 9728/6750).
8. **Two more real bugs found chasing that same connector attempt's follow-up failure** ("Authorization with Counter Pay MCP failed", reference `ofid_f33b30fbe5640a28`) — neither turned out to be the actual cause, but both are real and now fixed:
   - **PR #29**: Fly's edge proxy adds `X-Forwarded-For`; without a trust-proxy hop count configured at BOTH the Fastify level (`server-factory.ts`'s new `trustProxy: 1`) and the Express level (`oauth-router.ts`, mounted via `@fastify/express`), every real client behind Fly's edge silently shared one IP-keyed rate-limit budget instead of getting their own. Proved by reading `express-rate-limit`'s source and a standalone repro that `@fastify/express` copies its OWN already-resolved `request.ip` onto the raw request object before Express ever sees it — Express's own trust-proxy setting alone cannot fix the actual rate-limiting behavior, only the express-rate-limit warning log. The regression test in `server.test.ts` asserts on the `ratelimit-remaining` header, not a status code, because a bare "did it still respond" check passes whether or not this bug is present (confirmed: the underlying validation error never actually broke a request — it was always caught and only logged).
   - **PR #30**: `handleUpstreamCallback()`'s catch block deliberately never leaks Auth0 failure detail into the browser redirect (correct), but was ALSO not logging it server-side at all — a real upstream failure left zero trace anywhere. Added an injectable `onUpstreamCallbackError` callback (`provider.ts`), wired to `console.error` in `main.ts`.
9. **The actual cause of that specific failure, found by directly querying the real Auth0 tenant's error redirect and cross-referencing real Fly logs**: `counter-control-plane-api` was **crash-looping** — missing the `CONTROL_PLANE_SIGNER_KID`/`CONTROL_PLANE_SIGNER_SEED` Fly secrets that a recent PR (#25's revocation-envelope-signing work) had made mandatory in a production-like `NODE_ENV`, and Fly had given up restarting it after 10 failed attempts. Since Auth0's "Counter Onboarding" Post-Login Action calls `POST /control/v1/wallet-users/provision` on that exact app to create the wallet_user identity, every real login attempt hit a completely dead backend, which Auth0 surfaced as `access_denied` / `ACTION_ERROR_TIMEOUT: Action execution timed out` — a real, current production outage entirely unrelated to remote-mcp, that had likely existed since PR #25 shipped. **Fixed by generating a real Ed25519 signing seed and setting it as Fly secrets** (never displayed in any visible output — generated and written directly to a gitignored temp file, read into env vars, passed to `flyctl secrets set`, temp file deleted). Confirmed via a clean boot in fresh `flyctl logs`.
10. **A second, real, silently-blocking bug found via browser automation against the real deployed app** (not curl — curl doesn't reproduce browser CORS behavior): `/mcp` is a native Fastify route, NOT part of the MCP SDK's Express-mounted OAuth routers (which bundle the `cors` npm package internally — confirmed by reading their source), so it had ZERO CORS handling. A browser-based client's `OPTIONS /mcp` preflight got 401'd by `authPlugin` (which ran for every method including OPTIONS — a preflight never carries credentials, so this was always wrong, everywhere, not just here) instead of getting a proper preflight response. The browser then never sent the real `POST /mcp` at all — completely invisible to our server, which is exactly why this and the previous bug were so hard to tell apart from "the server is fine, something else is wrong": both produce total silence in our own logs, for different reasons. **Fixed in PR #31**: `packages/http-api-kit/server-factory.ts` gained an opt-in `cors` option (registered before `authPlugin` specifically so its OPTIONS short-circuit runs first — `@fastify/cors`, new dependency), enabled only for `apps/remote-mcp` (`origin: true`, safe because `/mcp` authenticates via an explicit `Authorization` header the browser never attaches automatically, unlike a cookie). Verified live: `OPTIONS /mcp` went from 401 to a real `204` with correct `access-control-allow-*` headers. New regression test in `server.test.ts` asserts on the actual preflight response, not a proxy for it.
11. **A third real, ongoing-risk bug, found by the SAME control-plane-api crash-loop fix not being sufficient** — after #9's fix, `counter-control-plane-api` no longer crashed, but it still scaled to zero on idle (`min_machines_running = 0`, same as every other app here). A cold start measured at ~7-9s is longer than whatever execution timeout Auth0 enforces on a Post-Login Action's outbound HTTP call, so a login attempt landing while that app happened to be asleep still failed with the same `access_denied` / `ACTION_ERROR_TIMEOUT` as #9 — reproduced for real (a fresh DCR registration in the DB ~5 minutes after the app had gone idle again, immediately followed by the same "Authorization failed" the founder saw). **This is a real, ongoing tradeoff, not a one-time bug** — flagged to the founder directly rather than silently fixed, given it has a recurring cost: `fly.control-plane-api.toml` now has `min_machines_running = 1`, `auto_stop_machines = false` (founder explicitly approved the ~$2/month cost 2026-09-03, same tradeoff already made for `counter-vault`'s own always-on config). Deployed directly (`flyctl deploy`), config committed to `main` outside the PR-per-bugfix pattern above since it's infra config, not testable application code.

**Deployed and live:**

- `counter-remote-mcp` (Fly) — public, single machine (`min_machines_running = 0`, confirmed auto-stops when idle in the logs). Health, OAuth metadata, and `/mcp` 401-without-token all verified against the live URL.

## 3. Critical operational gotchas hit this session (don't rediscover these the hard way)

- **`flyctl` commands that touch real infrastructure get inconsistently blocked by the auto-mode permission classifier** — `flyctl deploy`, `flyctl ssh console -C "..."` for anything destructive-looking (e.g. `rm -rf`), and `flyctl secrets import` via stdin all hit this at different points, sometimes passing on retry, sometimes not. When blocked, ask the founder to run the exact command rather than working around it.
- **`flyctl ssh sftp put` has a real bug on Windows** (at least via Git Bash and PowerShell in this session): it sometimes computes the wrong remote destination path, silently failing with a confusing `file does not exist` error unrelated to the actual paths given. Multi-line heredocs piped through `flyctl ssh console -C "..."` also fail — nested quoting between PowerShell, flyctl's own arg parser, and the remote shell breaks reliably. **What actually works:** the founder opens `flyctl ssh console --app <app>` interactively themselves and pastes a `cat > file << 'EOF' ... EOF` heredoc block directly at the prompt. Slower, but it sidesteps every quoting/encoding issue at once.
- **PowerShell pipes a UTF-8 BOM to native processes by default**, which broke `flyctl secrets import`'s stdin parsing (`"﻿NAME" is not a valid secret name`). Setting `$OutputEncoding` didn't fix it. What worked: `flyctl secrets set NAME=VALUE NAME2=VALUE2 ...` as direct command-line arguments instead of stdin.
- **A Fly Machine's `/tmp` is the container's ephemeral filesystem, NOT the persistent volume.** A `flyctl deploy` (even just to change `vault-config.hcl`) replaces the container and silently destroys anything left only in `/tmp` — this cost a full Vault wipe-and-reinit this session (see `vault-config.hcl`'s own note). **Never leave the only copy of anything durable in `/tmp` on a Fly machine** — get it onto the operator's own machine (or the persistent volume, if appropriate for that specific secret) immediately.
- **Fly's private 6PN network is IPv6-only.** A service that binds only `0.0.0.0` (IPv4) will accept local/loopback connections fine (so `ssh console` health checks pass) but be silently unreachable from other apps in the org. Bind `[::]` (IPv6 wildcard; dual-stacks IPv4 loopback too) for anything meant to be reached over 6PN.
- **A fresh Fly app's first deploy creates 2 machines for HA by default**, even with `min_machines_running = 0` in `fly.toml` — costs nothing extra once both scale to zero, but `apps/remote-mcp`'s design (in-process OAuth/session state) genuinely breaks with >1 concurrent machine. Scaled down to 1 machine manually (`flyctl machine destroy <id>`) after the first deploy.
- **The Vault root token and unseal key must never be the only copy anywhere Claude can lose them** — they were generated, immediately handed to the founder to save in their own password manager, and never displayed in this session's own visible output (redirected straight to files, extracted via `grep`/`awk` server-side, never `cat`'d into a tool result). The `remote-mcp-signer` Vault token (scoped to sign/verify only, already proven to reject listing-all-keys and sys/admin access) is a different, much lower-stakes secret and is fine to have passed through a session's context and into `flyctl secrets set`.
- **The real deployed data partition is `COUNTER_ENV=test`**, not `"pilot"` or `"sandbox"` (both appear as decorative/descriptive strings elsewhere in scripts, not the actual partition) — confirmed by querying `merchant.scopes`/`wallet.mandates` directly against the real Supabase DB, and independently confirmed by the fact that the `COUNTER_ENV` secret's DIGEST on the newly-created `counter-remote-mcp` app matches `counter-control-plane-api`'s exactly once set to `"test"`.
- **A scale-to-zero Fly app is a real, silent dependency risk for anything time-sensitive that calls it.** Two different bugs this session (items 9 and 11) trace back to `min_machines_running = 0` on `counter-control-plane-api` — one because the app was fully crash-looping (unrelated to scaling), one because even a HEALTHY app's cold-start latency (~7-9s, consistent across every app measured this session) can exceed a caller's own timeout (Auth0 Actions, in this case). Before assuming "the deployed code is correct, so it'll work," check what's calling it under a tight timeout and whether that caller will tolerate a cold start.
- **`curl` cannot reproduce two categories of real client failure that mattered this session**: CORS preflight/response behavior (curl doesn't enforce or even send what a browser does) and a real interactive login session's Auth0 state (a curl request has no browser cookies, no prior session, nothing an SSO/silent-auth check could key off of). Both items 9 and 10 needed either real browser automation (Claude-in-Chrome, driving the actual `claude.ai` connector UI) or reading the real Auth0 redirect's error query params from a real attempt — static code reading and curl-based endpoint checks had already been exhausted and came up clean for both.
- **Fastify plugin/hook registration order matters for auth bypass, and it's easy to get backwards.** `@fastify/cors`'s OPTIONS short-circuit only works if it's registered BEFORE `authPlugin` — registering it afterward (e.g., from inside an app's own `index.ts`, after calling the shared `createHttpServer()`) runs its hook too late, since Fastify's root-level `onRequest` hooks fire in registration order regardless of which file registered them. This is why the `cors` option lives inside `packages/http-api-kit/server-factory.ts` itself (registered first, before everything else) rather than being bolted on per-app afterward.
- **`ScheduleWakeup`'s dynamic-loop mechanism works fine as a general "check back on an external event later" tool outside of `/loop`** — used it this session to space out check-ins while waiting on the founder to retry the connector, without burning a wakeup on every idle tick. Not its documented primary use case, but the tool itself doesn't distinguish.
