# Merchant policy engine, readiness manifest, Shopify order actions, and runtime API surface (v2)

All seven issues from the v1 review have been addressed. Tenant isolation via `verifyTenantAccess` checks the JWT scope's merchantId on every route. Recursive payload hashing uses a `canonicalize()` function that sorts keys at all nesting depths. The health evaluator now cross-checks manifest capabilities against readiness check kinds using a `CAPABILITY_REQUIRED_CHECKS` map. `engine-strict=true` is restored in `.npmrc` with `engines.node >= 22.14.0`. The idempotency store accepts `maxSize` and `ttlMs` with LRU eviction. Simulation uses `r.ruleId.startsWith("buyer_") || r.ruleId.startsWith("merchant_")` instead of hardcoded IDs. The control-plane policy POST parses `If-Match` for optimistic concurrency and returns 409 on version conflict.

Watch for: control-plane policy routes lack tenant isolation — any authenticated caller can manage any merchantId's policy (confirmed); tenant isolation in merchant routes has zero negative-path test coverage (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The merchant runtime routes now enforce tenant isolation at the route layer via `verifyTenantAccess`, which reads the JWT scope and compares `scope.merchantId` to the path parameter. However, the control-plane policy routes (`policy-routes.ts`) do not perform any equivalent check — they verify only that the caller has the `identity.scope.read` permission, not that the caller's scope includes the target merchantId. This is the same horizontal-privilege-escalation pattern the v1 review identified in the runtime routes, applied to the policy CRUD surface.

The tenant isolation implementation in merchant routes is correct but untested in the negative path. No test sends a token scoped to merchant A while requesting merchant B's resources. A regression that removes the `verifyTenantAccess` call would go undetected by the current test suite.

The idempotency store's eviction strategy evicts by insertion order (FIFO) rather than by access recency. The `lookup()` method does not promote entries to the tail of the Map, so a frequently-replayed idempotency key can be evicted while stale keys that were recorded later remain. This is documented as "LRU-style eviction" in the code comment, but the implementation is FIFO. For the default 10k-entry / 1-hour-TTL configuration this is unlikely to cause problems in practice, but it's an inaccuracy in the documented contract.

## Control-plane policy routes: no tenant isolation

The `policyRoutesPlugin` in `apps/control-plane-api/src/policy-routes.ts` registers `identity.scope.read` as the required permission for both POST and GET routes, but never extracts or validates the caller's scope against the `:merchantId` path parameter:

```typescript
// POST - Create/update policy
fastify.post(ROUTE_PREFIX, async (request: FastifyRequest, reply: FastifyReply) => {
  const params = request.params as Record<string, string>;
  const merchantId = params["merchantId"] ?? "";
  // ← no ownership check: any authenticated caller with identity.scope.read
  //   can write policies for any merchantId
```

The v1 review flagged the identical pattern in `merchant-routes.ts`, and it was fixed there with `verifyTenantAccess`. The same fix needs to be applied here. The test suite for policy-routes (`policy-routes.test.ts`) uses tokens scoped to `TEST_MERCHANT_ID` and only ever requests that same merchant's policy, so the gap is not exercised.

## Tenant isolation test gap

The `verifyTenantAccess` function in `merchant-routes.ts` correctly reads `actorContext.scope` and validates:
- `platform` scope → access all merchants
- `merchant` scope → access only the matching merchant
- other scopes → deny

But the test suite only creates tokens with `scope: { kind: "merchant", merchantId: TEST_MERCHANT_ID }` and requests `TEST_MERCHANT_ID`. No test verifies that a request to a different merchantId is rejected with 403. A regression that accidentally removes or weakens the tenant check (e.g., always returning `true`) would not break any test.
