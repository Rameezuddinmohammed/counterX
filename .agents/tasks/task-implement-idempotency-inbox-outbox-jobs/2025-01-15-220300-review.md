# Runtime infrastructure: idempotency, inbox/outbox, and PostgreSQL jobs

This change introduces the durable workflow backbone — idempotency keys, transactional outbox, inbox deduplication, and lease-based background jobs. The approach splits interfaces (synchronous, in `@counter/workflow`) from PostgreSQL implementations (async, in `@counter/data`), with in-memory variants used for testing. A new `runtime` schema migration creates six tables with strong CHECK constraints and partial indexes for claimable work. All 542 tests pass and the data package type-checks clean.

Watch for: outbox `claim()` behavioral divergence between in-memory and PostgreSQL implementations (confirmed), `eventVersion` type mismatch that will fail at INSERT time (confirmed), hardcoded `LIMIT 10` in the job claim SQL with no caller control (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The in-memory outbox `claim()` only returns events with status `"pending"`, while the PostgreSQL implementation claims both `"pending"` and `"failed"` events whose `next_attempt_at` has passed. This means the in-memory tests don't exercise — and can't validate — the retry-after-failure path that the production implementation provides. The test for "failed events are not claimable until nextAttemptAt" actually passes because the in-memory claim never returns failed events at all, masking a missing code path.

The `OutboxEventInput` interface defines `eventVersion` as `string` (tests pass "1.0.0"), but the migration creates `event_version` as `integer NOT NULL DEFAULT 1`. The PostgreSQL `append()` passes `input.eventVersion` directly as a bind parameter to the integer column. Any non-numeric version string will produce a runtime INSERT error. The in-memory path silently stores whatever string is passed, so tests don't catch this.

The PostgreSQL job `claim()` hard-codes `LIMIT 10` in its SQL. The interface signature accepts no batch-size parameter, so callers cannot tune throughput. This is likely intentional scaffolding but creates an implicit contract that won't be obvious to future consumers.

The `markFailed` method in `PostgresOutboxRepository` performs a SELECT (without `FOR UPDATE` or a transaction) followed by an UPDATE. If two callers race on the same event ID, the `attempts` counter could read a stale value, producing incorrect backoff scheduling.

<summary>Issues (4)</summary>

1. **Outbox claim divergence** — In-memory `claim()` only returns `"pending"` events; Postgres returns both `"pending"` and `"failed"`. Fix the in-memory implementation to also claim failed events past their `nextAttemptAt`, or the retry path is untested.
2. **`eventVersion` type mismatch** — Interface is `string`, DB column is `integer`. Either change the interface to `number` (and update tests/inputs) or change the migration to `text`.
3. **Hardcoded job batch size** — `LIMIT 10` in `PostgresJobRepository.claim()` is not configurable. Add a `limit` parameter to the `AsyncJobRepository.claim()` signature.
4. **`markFailed` read-then-write race** — `PostgresOutboxRepository.markFailed` does a bare SELECT then UPDATE without a transaction. Wrap in a transaction with `FOR UPDATE`, or use a single `UPDATE ... SET attempts = attempts + 1 RETURNING attempts` to make it atomic.

## Outbox claim semantics: in-memory vs PostgreSQL

The PostgreSQL outbox `claim()` query includes `WHERE status IN ('pending', 'failed')`, intentionally treating failed events whose backoff has elapsed as eligible for re-dispatch. The in-memory implementation's claim loop has:

```typescript
if (event.status !== "pending") continue;
```

This skips failed events entirely. The test "failed events are not claimable until nextAttemptAt" passes vacuously — it asserts that claim returns 0, which is true because the in-memory never returns failed events regardless of timing. The follow-up assertion "After nextAttemptAt, it should be claimable" claims again but the test doesn't assert the length is 1; it just confirms the call succeeds.

The result is that the retry-after-failure pathway has no test coverage in the in-memory suite, and the two implementations have observably different behavior for any caller relying on outbox retry semantics.

## eventVersion type boundary

The `OutboxEventInput` interface declares `eventVersion: string`, and the test fixtures use `"1.0.0"`. The migration:

```sql
event_version int NOT NULL DEFAULT 1,
```

In the `append()` method, `input.eventVersion` is passed as bind parameter `$3` to an integer column. PostgreSQL will reject any non-integer string with a type-cast error. The `outboxEventFromRow` mapper converts back with `String(row.event_version)`, so reads would work, but the insert path will fail at runtime for any semver-style version. The in-memory path stores the raw string, so tests pass without exercising the actual column constraint.

## PostgresOutboxRepository.markFailed atomicity gap

The method does:

```typescript
const selectResult = await this.database.query<{ attempts: number }>(
  `SELECT attempts FROM runtime.outbox_events WHERE id = $1`, [id]);
// ... compute newAttempts, backoff ...
await this.database.query(
  `UPDATE runtime.outbox_events SET attempts = $2 ... WHERE id = $1`, ...);
```

Both queries run on `this.database` (the pool-level connection, not inside `this.database.transaction()`). Between the SELECT and UPDATE, another caller could increment `attempts` on the same row, and this caller would overwrite it with a stale value. This can produce incorrect `next_attempt_at` scheduling. A single atomic UPDATE (e.g., `SET attempts = attempts + 1, next_attempt_at = clock_timestamp() + (interval '1 second' * power(2, attempts))`) or wrapping in a transaction with `FOR UPDATE` would close the gap.

## Hardcoded job claim batch size

`PostgresJobRepository.claim()` uses `LIMIT 10` in the SQL, meaning each call returns at most 10 jobs regardless of workload. The `AsyncJobRepository` interface signature:

```typescript
claim(types: readonly string[], leaseOwner: string, leaseDurationMs: number, now: Instant)
```

provides no way for the caller to specify a batch size. This limits throughput scaling — a busy worker must call `claim()` repeatedly in a loop to drain the queue, adding per-call transaction overhead. Adding a `limit` parameter (mirroring the outbox's approach) gives callers control without requiring SQL changes.
