# Observability package and Operations Console shell

The @counter/observability package gains its full runtime: OTel SDK factory, structured logger with PII redaction, 12 domain metrics, health check registry, typed operator command framework with role/permission/step-up enforcement, kill switches with scope evaluation, 9 alert definitions wired to runbook templates, and safe attribute helpers. The operations console Next.js app ships stub pages (fleet, incidents, queues, kill switches, support sessions, adapters) backed by a typed-but-empty API client. Security test suites verify no telemetry leakage (53 tests) and no cross-tenant command access.

Watch for: `redactObject` has no circular-reference guard — a self-referential log payload will stack-overflow in production (confirmed). The `pin` sensitive-key regex `/pin/iu` matches substrings like "spinning" and "opinion", over-redacting benign fields (confirmed). The operations console pages have no authentication gate — they render for any request that hits the Next.js server (likely, given the layout has zero auth middleware).

**Verdict**: NEEDS_CHANGES

## High-level view

The v1 findings are all addressed: permissions and step-up are enforced at runtime in `execute()`, error stacks are redacted via `redactString()`, the dead OTLP exporter is removed, environment is a resource attribute with OTLP configured via env var, and the phone regex is tightened to require `+` or parenthesized area code.

The redaction engine deep-walks logged objects but carries no `WeakSet`-based cycle detector. Any self-referential object (common in Node.js errors with cause chains or library-internal structures) passed to `logger.info(msg, data)` will blow the stack and crash the process.

The sensitive-key regex set includes `/pin/iu` which substring-matches any field containing "pin" — "spinning", "pinCode", "opinionScore", etc. This will silently swallow legitimate data in log output and metrics attributes, making debugging harder while providing no real security benefit over a word-boundary pattern.

The operations console ships as server-rendered pages with no auth layer. The FEAT-002 description calls it "separately authorized" but neither the layout, middleware, nor any page checks operator identity. This is acceptable as a deliberate shell-first approach only if authentication is tracked as a blocking prerequisite before any real data flows through the API client.

## Circular-reference crash in `redactObject`

`redactObject` recursively calls itself on every nested object value without tracking visited references:

```typescript
} else if (typeof value === "object" && value !== null) {
  result[key] = redactObject(value);
}
```

Node.js `Error` objects frequently have `.cause` chains or library-attached metadata that forms cycles. Any `logger.error("msg", { err })` where `err` has a circular chain will produce a `RangeError: Maximum call stack size exceeded` and terminate the process. The fix is a `WeakSet<object>` parameter threaded through the recursion:

```typescript
export function redactObject(obj: unknown, seen = new WeakSet<object>()): unknown {
  // ...
  if (seen.has(obj as object)) return "[CIRCULAR]";
  seen.add(obj as object);
  // proceed with recursion, passing `seen`
}
```

This is a production crash risk, not a theoretical concern — the logger is the first thing called in error-handling paths.

## Over-broad `pin` sensitive-key pattern

The pattern `/pin/iu` in `SENSITIVE_KEY_PATTERNS` matches any key containing the substring "pin" anywhere, regardless of word boundaries:

```
/pin/iu  → "spinning" ✓  "opinion" ✓  "pinCode" ✓  "repin" ✓
```

While over-redaction is safer than under-redaction for true secrets, this particular pattern will swallow operational data (job types, flag names, user-facing labels) silently, creating debugging blind spots. A word-boundary version (`/\bpin\b/iu`) or an enumeration of actual field names (`pin`, `pin_code`, `pinCode`) preserves intent without collateral damage.

The same argument technically applies to `/ssn/iu` (matches "assn" prefixed keys, "lesson" reversed, etc.) but in practice SSN-containing field names are less ambiguous and the over-match surface is narrower.

## Unauthenticated operations console pages

The layout renders navigation and page content with no session or identity check. `createOperatorApiClient()` is called unconditionally in every page. Once the API client returns real data (post-stub phase), any unauthenticated visitor hitting these routes sees fleet health, incident details, kill switch state, and support grant metadata. The `metadata.description` says "Separately authorized operations console" but no authorization is implemented or even stubbed.

A minimal fix for the shell phase: a Next.js `middleware.ts` that redirects unauthenticated requests, or a `requireOperator()` call at the top of each page that throws if no session is present (can return a no-op in dev). This prevents shipping a page structure that silently becomes a security gap when real data flows in.
