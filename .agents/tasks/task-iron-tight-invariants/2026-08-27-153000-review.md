## High-level view

The reconciliation key fix is correct end-to-end. The receipt now carries an explicit raw `idempotencyKey` (set from `payload.transactionId` in the lifecycle handler, distinct from the derived `ctr_transaction_` CounterId stamped as `transactionId`), the outbox receipt sink writes it into the payload and uses it as the outbox idempotency key, and the candidate source, recorder, `isResolved`, and candidate SELECT all key on it with a COALESCE fallback for legacy rows. The integration test drives the real handler so `deriveTransactionId` actually runs, asserts the stamped id is distinct from the raw key and well-formed, then confirms the scanner joins on the raw key and closes a real settled Shopify order — it would fail against the pre-fix code.

The production authorization gate is now wired as the default. `boot.ts` defaults the money-seam policy to `createProductionPolicy` scoped to the operating merchant, and `main.ts` calls `selectPaymentAuthorizationPort` with no policy override, so the deployed seam gets the real policy rather than allow-all. The policy enforces amount-vs-quote, mandate/authorization expiry, revocation, merchant scope, and the per-transaction plus rolling-24h limits via the real `enforceTransactionLimits`. The adversarial and data-integrity gated proofs now feed authority envelopes into that same `createProductionPolicy` and assert zero Shopify effect on denial, so they bind to enforced production behavior instead of inline predicates.

The cross-instance draft race is closed by a durable pre-claim. Before `draftOrderCreate`, the winner atomically inserts a `shopify.draft.claim` row under the existing UNIQUE index; losers poll the durable ledger for the winner's recorded draft and reuse it, or return INDETERMINATE if the winner has not yet recorded, never creating a second draft. The rewritten concurrency proof counts real `draftOrderCreate` invocations across two racing port instances via a shared spy and asserts exactly one.

Reconciliation is now idempotent for orphaned candidates: `no_provider_effect` is treated as terminal in both `isResolved` and the candidate SELECT, while `still_indeterminate` stays re-scannable so a later settlement can still close it.

The secret scan now persists and includes a real `transaction.receipt.v1` outbox row in the scanned material, and adds an egress test proving `redactAuthorization` hides the Basic-auth credential (with a base64-decode control confirming the redaction is load-bearing). The PAN detector was hardened to a 14-19-digit Luhn floor with GID path-segment exclusion so runtime 13-digit epoch-ms timestamps no longer trip it; the positive control confirms a real 16-digit card still fires.

### Reconciliation key mismatch (v1 issue 1) — fixed and genuinely proven

`TransactionReceipt` gained an explicit `idempotencyKey: string`, set from `payload.transactionId` at every `sink.record` call in `transaction-lifecycle.ts`, while `transactionId` remains `deriveTransactionId(payload.transactionId)` — a hashed `ctr_transaction_` CounterId. `main.ts`'s receipt sink writes `idempotencyKey` into the receipt payload and uses it as the outbox idempotency key. In `reconciliation-boot.ts` the candidate SELECT reads `COALESCE(payload ->> 'idempotencyKey', payload ->> 'transactionId')` (legacy fallback), the recorder writes `idempotencyKey`, and both the resolved-exclusion subquery and `isResolved` match on it. The step ledger is keyed on the raw reference, so the join now matches in the deployed wiring.

The integration test closes the v1 gap where both sides were hand-seeded with the same key. It drives the real `createTransactionLifecycleHandler` (so `deriveTransactionId` runs), asserts the persisted receipt's `transaction_id` is *not* the raw key and starts with `ctr_transaction_`, then runs the real scanner and asserts it resolves the raw-keyed candidate to `resolved_closed` against a real settled Shopify order. Against the pre-fix code — where the candidate keyed on the derived id — the ledger lookup would miss and this test would fail.

### Production authorization gate (v1 issues 2 and 5) — now the deployed default

`createProductionPolicy` (new `lifecycle-policy.ts`) enforces, before any external effect: amount-vs-quote (`request.amountMinor !== authority.quotedAmountMinor`), revocation (`revokedAtMs <= now`), mandate expiry, authorization expiry, wrong merchant scope, and per-transaction + rolling-24h limits via the real `enforceTransactionLimits` from `@counter/payment-sdk`. Each envelope predicate is skipped when its field is absent; the limit check always runs. `boot.ts` defaults `policy` to `createProductionPolicy({ operatingMerchantId: bundle.merchantId })` inside `selectPaymentAuthorizationPort`, and `main.ts` passes no override, so the deployed worker seam enforces these predicates rather than falling back to `ALLOW_ALL_POLICY`. An explicit override still wins for tests.

The authorization-adversarial and data-integrity proofs were rewritten to feed authority envelopes into the same `createProductionPolicy` and assert `declined` + `policy-declined:` reference + zero draft/finalize/mark-paid spy calls + zero ledger rows across over-limit, over-rolling, revoked, expired-mandate, expired-authorization, wrong-scope, and quote-tamper. These now bind to enforced production behavior, and `lifecycle-policy.test.ts` adds deterministic unit coverage for each predicate plus the clean-allow path.

One deployment caveat: the default rolling ledger is a fresh per-process `InMemoryTransactionLedger`, so the rolling-24h window is not shared across instances or durable across restarts — the per-transaction ceiling and envelope predicates are hard, but the rolling check is per-process best-effort unless a shared ledger is injected.

### Cross-instance draft race (v1 issue 3) — closed by a durable pre-claim

`PostgresStepLedger.claim` inserts a `${step}.claim` row (`shopify.draft.claim`, a distinct step that never collides with the `shopify.draft`/`shopify.finalize` lookups) under the existing `UNIQUE(environment, idempotency_key, step)` index with `ON CONFLICT DO NOTHING RETURNING id`; `won` is true only for the caller whose INSERT returned a row. In `real-lifecycle.ts`, when no draft is recorded yet, the winner calls `draftOrderCreate` and records the outcome; a loser calls `awaitDraftOutcome` (bounded poll of the durable ledger) and reuses the winner's reference, propagates `declined`, or returns `indeterminate("draft.claim.pending")` — never a second draft. No migration was needed.

The rewritten concurrency proof wraps the real `draftOrderCreate.execute` with a shared counter across two independent port instances (distinct in-memory caches, as two workers would have), races the same key plus a retry, and asserts `draftCalls === 1` — the true race invariant, not the v1 `ON CONFLICT`-trivial single-ledger-row assertion. A non-gated `real-lifecycle.test.ts` case exercises the same at-most-once race against a mocked network.

### Terminal disposition (v1 issue 4) — reconciliation now idempotent for orphans

`isResolved` and the candidate SELECT now treat both `resolved_closed` and `no_provider_effect` as terminal, so a permanently orphaned candidate (a receipt with no durable order reference that will never gain one) is excluded from future passes instead of appending a new `transaction.reconciliation.v1` row every 60s. `still_indeterminate` (an order that exists but is not yet settled) deliberately stays re-scannable so a later settlement closes it. Deterministic unit tests were added.

### Secret scan (v1 issue 6) — outbox rows and egress now covered

The scan persists a real `transaction.receipt.v1` outbox row exactly as the deployed receipt sink writes it and includes `outboxRows.rows` in the scanned material alongside logs, result, and ledger rows, then asserts zero hits. A new egress test drives the real `redactAuthorization` from `@counter/razorpay-adapter`: it builds the actual `Basic <base64(keyId:keySecret)>` header, asserts the redacted form is `Basic [REDACTED]` and leaks nothing, and — the fix in 554617f — base64-decodes the raw header to confirm it genuinely carries the plaintext secret, so the scanner is not vacuously passing on already-clean input.

The PAN detector was hardened to a 14-19-digit Luhn floor with a preceding-slash (GID path-segment) exclusion, because the runtime emits 13-digit epoch-ms timestamps that are coincidentally Luhn-valid and now flow into the scanned outbox rows. The positive control plants `4111111111111111` (a Luhn-valid 16-digit Visa test PAN) and asserts the detector still fires, so hardening did not blind the scanner to a real card.

### Explicit-outcome semantics and baseline

Every indeterminate branch (draft, razorpay order, payment authorize/capture, finalize, mark-paid) returns via `indeterminate(...)` with no `stepLedger.record`, so an unknown state is never persisted terminal and stays re-drivable — a `failed` finalize is deliberately surfaced as indeterminate (payment already captured) rather than declined. Non-gated worker (70 pass / 20 skip) and data (25 pass / 5 skip) suites are green, integration suites skip cleanly without credentials, worker/data typecheck cleanly, and depcruise reports 0 violations across 2119 modules. The pre-existing `apps/merchant-console` / `apps/operations-console` typecheck failures under `exactOptionalPropertyTypes` are in UI files this milestone does not touch and are out of scope.
