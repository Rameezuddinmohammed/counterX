# Iron-tight invariants: durable ledger, kill switches, reconciliation, and adversarial proofs

Three features harden the real transaction lifecycle: a durable per-step ledger (migration 0007) so the Shopify draft/finalize/mark-paid legs dedup across worker restarts; durable operator kill switches (migration 0008) consulted before any external effect; a periodic reconciliation job that resolves INDETERMINATE transactions against authoritative Shopify order evidence; and a suite of creds+DB-gated adversarial, tenant-isolation, and secret-leakage integration proofs against the real path. The durable-ledger and kill-switch mechanisms are correctly built and genuinely proven, explicit outcomes are preserved (indeterminate is never persisted as terminal), and the RLS proof uses a real no-bypass role. Build, depcruise (2113 modules), and the non-gated test suites are green; every integration test skips cleanly without credentials.

Watch for: (1) **confirmed** — the reconciliation candidate source keys the step-ledger lookup on the receipt's `transactionId`, which the lifecycle writes as a *derived* CounterId, while the ledger is keyed on the *raw* `payload.transactionId`; the two never match, so in the deployed wiring reconciliation can never find the order reference and every candidate degrades to `no_provider_effect` — the reconciliation objective is defeated in production even though its integration test passes. (2) **confirmed** — the worker money seam's authorization/limit/mandate/quote-tamper gate is a `LifecyclePolicyPort` that production wires as allow-all; the adversarial deny proofs inject their own denying policies, so they prove the gate-to-zero-effect wiring but not that the deployed worker path enforces any of these predicates. (3) **likely** — the concurrency proof asserts one ledger row (trivially guaranteed by `ON CONFLICT`) but does not query Shopify to confirm one draft order; a true two-worker race can still create two drafts because cross-instance draft dedup relies on Shopify server-side idempotency the connector does not provide.

**Verdict**: NEEDS_CHANGES

## High-level view

The durable step ledger is the load-bearing change and it is sound. `PostgresStepLedger` records only terminal (`completed`/`declined`) outcomes under a `UNIQUE(environment, idempotency_key, step)` index with `ON CONFLICT DO NOTHING`, and the real lifecycle consults it before each Shopify effect, replaying a recorded outcome instead of re-driving. Indeterminate steps are deliberately never recorded, preserving re-drivability. The crash-simulation integration test forces finalize to throw after a real draft, then resumes on a fresh port and asserts the draft reference is unchanged — a proof that would fail against the previous in-memory Map.

The kill-switch gate is consulted first in the money seam, before the policy gate and before any Shopify or Razorpay call, and its adapter fails closed (throws) on a store error. The integration test activates a real durable merchant switch and asserts a blocked outcome with zero ledger rows.

The reconciliation job's decision logic is correct in isolation — it only ever produces `resolved_closed` from a real settled Shopify order and never fabricates success — but its deployment wiring reads the wrong key. Receipts are written with a derived transaction CounterId while the step ledger is keyed on the raw payload reference, so the production candidate→ledger join cannot match. The unit and integration tests seed both sides with the same key and therefore never exercise the mismatch.

The authorization adversarial proofs are structurally valid but test a policy seam the production worker leaves permissive: `main.ts` passes no policy override, so the deployed `RealLifecycleConfig` uses `ALLOW_ALL_POLICY`. Over-limit uses the real `enforceTransactionLimits`, but revocation, expiry, scope, and quote-tamper are encoded as inline test predicates. The data-integrity CTP receipt proof and the resilience webhook proof (real HMAC verify plus real Postgres inbox dedup) are genuinely independent and would fail if reverted.

Tenant isolation is proven through Postgres RLS with a dedicated NOSUPERUSER/NOBYPASSRLS/NOINHERIT login role whose posture is asserted, driving claim-scoped transactions that show cross-tenant and cross-environment invisibility. The secret-leakage scan is pure-Node with a positive control, covering env literals plus `shpat_`/`rzp_test_`/Luhn-valid-PAN/CVV/UPI patterns across logs, result, and ledger rows.

<summary>Issues (6)</summary>

1. **Reconciliation key mismatch (blocking)** — the candidate source uses the receipt's `transactionId` (a derived `ctr_txn_<hash>` CounterId from `deriveTransactionId`) as the step-ledger lookup key, but the ledger is keyed on the raw `payload.transactionId`; they never match, so reconciliation always resolves `no_provider_effect` and can never close a real INDETERMINATE order. Either record the raw `payload.transactionId` in the receipt payload (or an explicit `idempotencyKey` field) and read that in `createPostgresCandidateSource`/`createPostgresLedgerReader`, and add a test that drives the real handler end-to-end rather than seeding both sides with the same key.
2. **Production authorization gate is allow-all** — `main.ts` calls `selectPaymentAuthorizationPort(process.env, undefined, {...})` with no `policy`, so the deployed worker seam uses `ALLOW_ALL_POLICY`; the over-limit/revocation/expiry/scope/quote-tamper denials are only enforced by test-injected policies. Wire a real policy (limits + mandate/authorization + amount-vs-quote check) into the production path, or document where upstream (checkout-orchestrator) enforcement gates the job before it reaches the worker and prove that path.
3. **Concurrency proof does not confirm one Shopify draft** — the test asserts exactly one `shopify.draft` ledger row, which `ON CONFLICT DO NOTHING` guarantees regardless of how many real drafts were created; cross-instance draft dedup relies on Shopify server-side idempotency the connector's in-memory `IdempotencyStore` does not provide. Query Shopify for orders tagged with the idempotency key (or count drafts) to prove a true race creates one order, or gate the draft behind a durable pre-claim so two workers cannot both call `draftOrderCreate`.
4. **Reconciliation re-records non-closed dispositions unboundedly** — `isResolved` only treats a prior `resolved_closed` event as resolved, and the candidate SELECT only excludes transactions with a `resolved_closed` follow-up, so a permanently orphaned INDETERMINATE (e.g. `no_provider_effect`) appends a new `transaction.reconciliation.v1` outbox row every pass forever. Treat terminal non-closed dispositions as resolved (or add a backoff/attempt cap) so the scan is idempotent for unresolvable candidates.
5. **Revocation and quote-tamper predicates are simulated, not enforced** — the revocation-midflight test injects an indeterminate `paymentRecord` and the data-integrity amount-tamper test uses an inline `req.amountMinor === quotedAmountMinor` policy; neither exercises a production revocation or quote-recompute predicate. Fold these into the real policy from issue 2 so the proofs bind to enforced behavior.
6. **Secret-leakage scan omits network egress and outbox rows** — the scan covers `console.*`, the returned result, and `lifecycle_steps` rows, but the header comment claims outbox/inbox rows are scanned "when present" while the material array excludes them, and outbound Shopify/Razorpay request headers (where the token/secret actually travel) are not captured. Add the outbox rows to the material set and, if feasible, assert redaction on the connector's request-logging path.

<summary>Details</summary>

### Durable step ledger closes the cross-restart duplicate gap

Only terminal outcomes are recorded; every indeterminate branch returns without a `record` call, so an unknown state stays re-drivable — the resilience test confirms an indeterminate finalize leaves zero `shopify.finalize` rows. The crash-simulation test is the real proof: attempt A runs a real draft then throws in finalize, recording the draft in Postgres; attempt B builds a fresh port (a fresh in-memory cache, as a restart would have) against the same durable ledger and asserts the resumed draft reference equals attempt A's. Against the previous in-memory Map this would re-create the draft and the references would differ.

One defensive gap: a replayed `completed` draft or finalize uses `reference ?? ""`, so a `completed` row with a null reference would propagate an empty `draftOrderId`/`orderId` downstream rather than surfacing an error. This should not occur (completed steps always carry a reference) but is an unguarded assumption.

### Kill-switch gate precedes every external effect

In `authorizeAndCapture` the kill-switch check sits at the top (step 2a), before the policy gate, before `draftOrderCreate`, and before the Razorpay `createInstruction`. On a store error `createPostgresKillSwitchGatePort` throws, so the breaker fails closed rather than letting a checkout through. Migration 0008's partial unique indexes separate the platform (NULL entity) and scoped cases, and `recordActivate` branches its `ON CONFLICT` target to match. The integration test asserts blocked plus zero ledger rows, which would fail if the gate ran after the draft.

### Reconciliation logic is correct but its deployment wiring reads the wrong key

`reconcileCandidate` never fabricates a closed outcome: no durable order reference → `no_provider_effect`; an inconclusive `orderQuery` → `still_indeterminate`; a settled order (PAID/PARTIALLY_REFUNDED/REFUNDED) → `resolved_closed`; otherwise `still_indeterminate`.

The defect is in `reconciliation-boot.ts`. `createPostgresCandidateSource` selects `payload ->> 'transactionId'` from `transaction.receipt.v1` events and uses it verbatim as `idempotencyKey`. But `main.ts`'s receipt sink writes `transactionId: receipt.transactionId`, and `transaction-lifecycle.ts` sets `transactionId = deriveTransactionId(payload.transactionId)` — a hashed `ctr_txn_<...>` CounterId — while the step ledger is written with `idempotencyKey: payload.transactionId` (the raw opaque reference). So `createPostgresLedgerReader.lookup(derivedId, "shopify.finalize")` queries `runtime.lifecycle_steps` for an `idempotency_key` that was never inserted; it returns undefined and the candidate degrades to `no_provider_effect`. In the live deployment reconciliation therefore never finds the authoritative order and can never resolve an INDETERMINATE transaction to closed — the stated purpose of FEAT-002.

The integration test does not catch this because it seeds both the receipt payload's `transactionId` and the `lifecycle_steps.idempotency_key` with the same raw string and never invokes the handler, so `deriveTransactionId` is never applied. It creates and queries a live settled Shopify order, but validates the scanner against a hand-consistent key space, not the one the handler produces.

Compounding this, `isResolved` only returns true for a prior `resolved_closed`, and the candidate SELECT only excludes transactions that already have a `resolved_closed` follow-up. A candidate that resolves to `no_provider_effect` or `still_indeterminate` is re-selected and re-recorded on every 60s pass, so an unresolvable orphan accretes reconciliation outbox rows without bound.

### Adversarial authorization proofs test a seam production leaves permissive

The six adversarial cases inject a `LifecyclePolicyPort` and assert `declined` + zero spy calls + zero ledger rows, proving a deny decision produces zero external effect. The over-transaction and rolling-24h cases call the real `enforceTransactionLimits` against a real in-window ledger. But revocation (`revokedAt <= now`), mandate/authorization expiry, and wrong-scope are inline boolean predicates in the test, and the data-integrity amount-tamper case is an inline `req.amountMinor === quotedAmountMinor` policy.

The gap is that `main.ts` wires the production port with no policy override, so the deployed `RealLifecycleConfig` falls back to `ALLOW_ALL_POLICY` — the worker money seam itself enforces none of limits, revocation, expiry, scope, or amount-vs-quote. `enforceTransactionLimits` is invoked in `payment-sdk`'s `checkout-orchestrator.ts`, a separate path; whether the worker job is gated by it upstream is neither wired here nor proven by these tests. As written, the adversarial suite would still pass even if the deployed worker performed no authorization at all, because it never exercises the deployed policy.

The revocation-midflight test models revocation by returning an indeterminate `paymentRecord`; it is a valid proof that a blocked consequential step surfaces INDETERMINATE with one draft, one finalize, and no mark-paid row (no compounding effect), but the "revocation" is simulated rather than enforced by a production predicate.

### Concurrency proof under-verifies the draft

Two separate port instances (distinct in-memory caches, as two workers would have) share one Postgres ledger and fire the same key concurrently plus a racing retry. The assertions are exactly one `shopify.draft` row and one `shopify.finalize` row. But `ON CONFLICT DO NOTHING` guarantees one *ledger* row no matter how many real drafts were created, and each attempt that finds `draftLedger === undefined` calls `draftOrderCreate` before any row exists. The connector's `IdempotencyStore` is per-action-instance in-memory, so two instances do not share it, and the Shopify Admin `draftOrderCreate` mutation has no native idempotency key. A genuine two-worker race can create two Shopify drafts even though only one ledger row survives, and the test does not query Shopify to confirm a single draft order. (Post-draft steps are safe because finalize/mark-paid consult the ledger after the draft row exists.)

### Genuinely independent proofs: CTP receipt, webhook, RLS, secret scan

The data-integrity receipt tests use the real `verifyEnvelope` from `@counter/trust-protocol` and reject both a tampered payload and a tampered signature (asserting `UNAUTHENTICATED`) — an independent cryptographic verifier, not a local boolean. The resilience webhook test drives the real Razorpay `verifyWebhook` HMAC path (including a tampered-signature rejection) and then the real `PostgresInboxRepository.receive` with `ON CONFLICT DO NOTHING`, asserting duplicate/reordered deliveries collapse to one row. The tenant-isolation test creates a real NOSUPERUSER/NOBYPASSRLS/NOINHERIT login role, asserts its posture, connects as it (preserving the Supabase pooler project-ref suffix), and drives claim-scoped transactions proving A cannot see B, a guessed cross-tenant id returns not-found, and a sandbox identity is invisible to a test-environment claim — it would fail if RLS policies were absent. The secret-leakage scan's positive control would catch a broken scanner; its scope is what the runtime emits and persists (logs, result, ledger rows), not connector network egress (see issue 6).

### Migrations and bundled fixes

Migrations 0007/0008 carry CHECK constraints and partial unique indexes; the down files are plain `DROP TABLE`, consistent with the existing migration style. The migration-count test expectations were updated from 4 to 8 and the RLS test's expected version to 8, matching the two new migrations. The bundled Shopify `orderCancel` fix adds the now-required `restock: false` argument for Admin API 2025-07 — a correctness fix that also makes the tests' order cleanup work, so it is appropriately in scope rather than an unrelated change.
