# Merchant Console Transactions wired to a live read-model projection (v2)

Replaces the hardcoded `DEMO_TRANSACTIONS` array on the merchant-console Transactions page with a real `useApi(listTransactions)` fetch, backed by two new control-plane-api GET endpoints. The endpoints assemble the fixed front-end `Transaction` shape from a merchant-scoped read-model over `runtime.workflow_intents` (spine), `runtime.lifecycle_steps` (state/transitions), and `runtime.spend_ledger` (amount, minor→major /100). Tenant isolation is enforced server-side for both list and get-by-id, the routes mirror the established `policy-routes.ts` pattern, and the projection is proven against live Supabase with a creds/DB-gated integration test that seeds and cleans up its own rows.

Watch for: the list query can emit **duplicate transactions** when a single `transaction_id` has more than one `workflow_intents` row (the dedup index keys on `transaction_id + command_type + command_digest`, not `transaction_id`) — *likely*, dormant only because the current lifecycle writes one intent per transaction. The amount lookup picks an arbitrary single `spend_ledger` row per reference when more than one wallet has ledgered against it — *possible*. Both are latent given today's empty tables and single-command reality; neither breaks the slice as delivered. Everything the task scoped is present, correct, and tested.

**Verdict**: APPROVED

## High-level view

The read model is a spine-and-satellites join: `workflow_intents` filtered to `environment + scope_kind='merchant' + scope_id` supplies the transaction identity and status; `lifecycle_steps` (joined by `idempotency_key = transaction_id`) supply the ordered Shopify legs that drive state derivation; `spend_ledger` (joined by `reference = transaction_id`) supplies the amount. State is derived by a pair of pure, documented functions grounded in the worker's real `shopify.draft/finalize/markPaid` step names, with `.claim` guard rows excluded from user-visible transitions.

Tenant isolation is asymmetric by necessity and correct: list scopes in SQL and up-front-checks the path `merchantId` against the caller's scope (403 on mismatch); get-by-id can't scope in SQL because the caller supplies only a transaction id, so it resolves the intent, then compares the owning `scope_id` to the caller and returns a non-disclosing 404 on mismatch or unknown id. Platform scope bypasses both, matching `policy-routes.ts`.

The front-end contract was fixed and is honored exactly — the API-layer `Transaction`/`TransactionState`/`TransactionStateTransition` types are byte-for-byte copies of `merchant-console/src/lib/types.ts`, and the routes return raw array / raw object bodies as `api-client.ts` expects.

The known gaps are honest, not defects: `buyerRef` and `method` have no persisted column, so they read from `authority_context` when present and fall back to explicit `(unavailable)`/`unknown` placeholders rather than fabricated values. Production-like environments fail closed — the server refuses to start without a durable transaction store injected, mirroring the pre-existing policy-store invariant.

The two latent correctness gaps (duplicate rows on multi-intent transaction ids; arbitrary amount row on multi-wallet references) are the only things worth a follow-up, and both are consequences of schema shape the projection doesn't yet guard against.

<details>
<summary>Issues (4)</summary>

1. **Duplicate transactions on multi-intent id** — `list` returns one `Transaction` per `workflow_intents` row, but the uniqueness key is `(environment, transaction_id, command_type, command_digest)`, so two intents sharing a `transaction_id` produce two identical-id rows. Dormant today; add a `DISTINCT ON (transaction_id)` or aggregate before shipping a second command type against the same transaction.
2. **Arbitrary amount row on multi-wallet reference** — `loadAmount` takes `ORDER BY id ASC LIMIT 1`, so if a `transaction_id` (reference) is ledgered against more than one wallet the surfaced amount is whichever inserted first. Decide whether amount should sum across wallets or be scoped to a specific wallet, and make the selection deterministic/intentional.
3. **N+1 query fan-out on list** — each intent triggers two extra sequential queries (steps + amount); at `limit=200` that is up to 401 round-trips per list call. Consider batching steps/amounts into two `WHERE ... IN (...)` queries. Not blocking at pilot volume.
4. **`getTransaction` route is unreachable from the console today** — the endpoint and its tenant check are implemented and tested, but no console page calls `getTransaction`; it exists ahead of a detail view. Informational — flagged so it isn't mistaken for dead code.

### Read-model projection and state derivation

`deriveTransactionState` and `buildTransitions` are pure functions with the mapping documented at the top of `transaction-routes.ts`, and the step constants (`shopify.draft/finalize/markPaid`) match `apps/worker/src/real-lifecycle.ts` exactly, so the derivation is grounded in what the worker actually writes rather than invented. State collapses to `settled`/`captured`/`authorized` on the highest completed leg, and to `failed` on either `intent.status='failed'` or any `declined` step; `.claim` guard rows are filtered before both derivation and transition building. `refunded` and `disputed` are part of the front-end union but have no persisted source, and the code correctly never derives them rather than faking a mapping.

`buildTransitions` always anchors a synthetic `from:null → initiated` at the intent's `created_at`, then chains each visible step so `from` links to the previous `to`, carrying `lifecycle_steps.reference` as `evidenceRef` and attributing `shopify.*` steps to the `shopify` actor. The integration test drives the full `draft→finalize→markPaid` sequence (plus a `.claim` guard) through live rows and asserts the exact `["initiated","authorized","captured","settled"]` ordering with the reference threaded through, so this is proven against real data, not just fixtures.

The minor→major conversion reads `amount_minor` as a string (the pg driver returns `bigint` columns as strings) and converts via `BigInt(...)/100`, avoiding float truncation on the wide integer before the final divide. The integration test seeds `150000` minor and asserts `1500` major end-to-end.

### Tenant isolation across list and get-by-id

The two paths enforce scope differently because they have different information. `list` receives the target `merchantId` in the path and both filters the SQL by `scope_id` and rejects a caller whose merchant scope doesn't match with a 403 before touching the store. `get` receives only a transaction id, so it resolves the intent first, then compares the resolved `scope_id` against the caller's scope; on mismatch or unknown id it returns an identical 404 so a merchant cannot probe for the existence of another merchant's transaction. Platform scope short-circuits to allowed in both, consistent with `verifyTenantAccess` in `policy-routes.ts`. Unauthenticated requests never reach the handlers — the 401 comes from the pre-existing global auth layer, and the tests confirm it for both routes.

The unit suite mints real RS256 tokens against a local JWKS (mirroring `policy-routes.test.ts`) and covers cross-merchant list (403), get of another merchant's id (404, non-disclosing), unknown id (404), owned get (200), and platform-scope access to any merchant. The integration test repeats the isolation assertions against live rows for a second merchant B — empty list, 403 on cross-merchant list, 404 on get-by-id. These would all fail if the `verifyTenantAccess` checks were removed, so they are not tautological.

### Duplicate-row and amount-selection gaps

Both routes assume one intent per `transaction_id` and one ledger row per reference, but the schema permits neither. `workflow_intents_dedup` is unique on `(environment, transaction_id, command_type, command_digest)`, so a transaction that ever produces two intents (a second command type, or a re-digest) yields two rows with the same `transaction_id`. `list` maps rows one-to-one, so the console would show two entries with identical ids; `get` masks it with `ORDER BY created_at DESC LIMIT 1` but then silently picks the newest intent's status. Similarly `spend_ledger` is unique on `(environment, wallet_id, reference)`, so `loadAmount`'s `ORDER BY id ASC LIMIT 1` surfaces whichever wallet ledgered first. Neither can fire today — the tables are empty and the live lifecycle writes exactly one intent and one ledger row per transaction — which is why this is a latent design gap rather than a bug in the delivered slice. A `DISTINCT ON (transaction_id)` on the list spine and an explicit aggregation-or-scoping decision on the amount would close both.

### Fixed front-end contract adherence

The API-layer types in `transaction-routes.ts` are an exact structural copy of `merchant-console/src/lib/types.ts` (same union members, same `readonly` fields, `currency` pinned to the `"INR"` literal), and the route bodies are raw — `reply.send(transactions)` for the array and `reply.send(owned.transaction)` for the single object — which is what `api-client.ts` parses directly into `readonly Transaction[]` / `Transaction`. The route paths (`/merchants/:merchantId/transactions`, `/transactions/:transactionId`) line up with the client's request paths under the shared base URL. The page consumes the contract through `useApi(client => client.listTransactions(MERCHANT_ID), [MERCHANT_ID])` and renders skeleton/error/empty/data branches with `@counter/ui` primitives; `MERCHANT_ID` comes from `NEXT_PUBLIC_MERCHANT_ID` with the pilot fallback, and the comment correctly notes the real tenant boundary is the server-side token scope, not this client value.

### Documented gaps and fail-closed wiring

`buyerRef` and `method` read from `authority_context` when a non-empty string is present and otherwise emit `(unavailable)`/`unknown` constants rather than fabricated identifiers — the honest choice given no persisted column exists, and the integration test confirms the present-in-`authority_context` path. Environment wiring fails closed: `resolveTransactionStore` throws in production-like environments unless a durable store is injected, and `index.test.ts` was updated to assert both the throw (policy store alone is insufficient) and the success path with both stores injected — a guard that would regress visibly if removed. `main.ts` injects the Postgres store built from `DATABASE_URL` alongside the policy store.

### Scope and incidental changes

The only change outside the slice is `use-api.ts` switching its two relative `../lib/api-client.js` imports to the `@/lib/api-client` alias. Per the feature findings this is a forced Turbopack resolution fix that surfaced only once the Transactions page pulled the hook into a built page graph; it's a no-op on behavior and contract. The local `SqlRow = Record<string, unknown>` in the Postgres store (rather than importing pg's `QueryResultRow`) is a deliberate choice to avoid adding a direct `pg` dependency edge that would trip depcruise. No other pages or consoles were touched, which matches the slice boundary.
