## High-level view

The Razorpay indeterminate path is now live. `RazorpayTestProvider.createInstruction` inspects the real HTTP client's synthetic 503 body: a `reason:"timeout"` marker becomes `kind:"indeterminate"` (with a +30s re-query window), while `reason:"network"` and every genuine Razorpay 4xx/5xx still throw the same `UNAVAILABLE` canonical error as before. Because the Razorpay order is created *after* the Shopify draft, this timeout is a genuine post-effect unknown, and the previously-dead `razorpayResult.kind === "indeterminate"` branch in `real-lifecycle.ts` now routes it to an INDETERMINATE result with a recorded receipt — never a collapsed failure. The existing error-mapping surface is untouched, which is why the prior adapter tests did not regress.

The signed evidence now travels the whole seam. The lifecycle extracts `evidence.providerData.envelope` (the CTP `counter.evidence.v1` envelope), returns it on the captured outcome, and the handler records it on `TransactionReceipt.signedEvidence` across the captured, indeterminate, and reconciliation-mismatch sink calls. The envelope carries references, status, and signature material only — no PAN/CVV/UPI PIN/secrets — and the `verify:real` script prints it, warning when absent.

Reconciliation is now like-for-like. The Shopify order total (variant price × qty, catalog-derived) is preserved as audit evidence on the provider reference (`shopify_total_minor:...`) but no longer drives the comparison. The reconciled amount is the amount handed to the payment rail, compared against intent, so a genuine success reconciles even when the order total differs; a mismatch still transitions to INDETERMINATE with a retryable `reconciliation.mismatch`. The caveat is that the real port defines the captured amount *as* the intended amount, so its own reconciliation can never mismatch — the independent-amount check is meaningful only for ports that report an externally-observed capture.

Cross-restart idempotency for the Shopify legs (#5) is documented in the `real-lifecycle.ts` header as a known limitation deferred to durable-resume, with within-process at-most-one-effect still proven by the replay test. Razorpay's server-side idempotency key remains the only cross-restart guard, unchanged from v1.

### Razorpay timeout now reaches the indeterminate branch; real API errors still throw

On a non-200 the provider extracts the transport marker before deciding:

```ts
const transportReason = extractTransportReason(response.body);
if (transportReason === "timeout") {
  const queryAfter = futureInstant(this.#clock, RETRY_AFTER_MS);
  return Object.freeze({ kind: "indeterminate", reference: command.idempotencyKey, queryAfter });
}
throw createCanonicalError({ code: "UNAVAILABLE", category: "unavailable", ... });
```

`extractTransportReason` only recognizes the `{ error: { reason: "timeout" | "network" } }` shape the real HTTP client synthesizes for a fetch/abort failure. A genuine Razorpay 4xx/5xx body has no such marker, so it falls through to the same thrown `UNAVAILABLE` — this is why the error-mapping and prior adapter tests are unchanged. `network` is deliberately *not* reclassified: the request never left the transport, so there is no possible external effect, and it stays a hard unavailable.

Ordering makes this a true post-effect case: `real-lifecycle.ts` creates the Shopify draft first, then the Razorpay order. When `createInstruction` returns `kind:"indeterminate"`, the branch that was dead in v1 now fires:

```ts
} else if (razorpayResult.kind === "indeterminate") {
  return indeterminate("razorpay.order.indeterminate", `razorpay:${key}`);
}
```

The handler records an INDETERMINATE-phase receipt and raises a retryable `payment.indeterminate` rather than collapsing to failed, and the payment/finalize/mark-paid legs never run — so the draft is created exactly once. Both new worker tests assert this: one at the port level (`status === "indeterminate"`, one draft, zero finalizes, transport hit once because indeterminate outcomes are not cached), one through the handler (retryable `payment.indeterminate`, one receipt in phase INDETERMINATE). Under the pre-fix provider these assertions fail because `createInstruction` threw.

### The signed envelope is carried, not just referenced

`extractSignedEvidence` pulls `evidence.providerData?.["envelope"]` and returns it, falling back to a minimal `{ reference, status, confirmedAt }` object when absent so the receipt always carries typed evidence. The lifecycle returns it on the captured outcome, and the handler sets `signedEvidence` on all three sink paths. The envelope is the CTP `counter.evidence.v1` structure whose payload is a `canonical_claim { reference, status }` plus issuance metadata — no card/UPI secrets. The new test asserts `receipt.signedEvidence.type === "counter.evidence.v1"` with a present `signature` and `payload`, and that the serialized receipt contains neither `secret` nor `shpat_`. Pre-fix, `signedEvidence` was undefined, so the test fails.

### Reconciliation compares payment amount against intent; order total demoted to audit

```ts
const shopifyOrderTotalMinor = toMinorUnits(orderResult.totalPrice, request.currency); // audit only
const capturedMinor = authorized.capturedMinor;                                        // reconcile this
```

`buildReference` appends `shopify_total_minor:${shopifyOrderTotalMinor}` so the catalog total survives as evidence without driving the comparison. The handler's unchanged check — `reconciled: providerResult.capturedMinor === payload.amountMinor`, mismatch → INDETERMINATE + retryable `reconciliation.mismatch` — still catches a genuinely divergent capture. The new success test sets the order-query total to `123.45` (12345 minor) against an intended 4999 and asserts the run closes CLOSED with `reconciled: true`, `providerAmountMinor === 4999`, and `shopify_total_minor:12345` on the reference. Pre-fix this run went INDETERMINATE (12345 ≠ 4999), so the test fails.

The residual gap: `authorizeCapture` derives `capturedMinor` from `request.amountMinor` on every branch, so the real port's own reconciliation is self-consistent by construction — it cannot detect a provider capturing a different amount than requested. The generic handler mechanism is intact for any port that reports an independently-observed amount, and the mock test-provider exercises that mismatch path. Wiring the real captured amount out of the CTP evidence or Razorpay order is the natural follow-up when a live capture connector lands; it is not a regression and does not block this task, whose deliverable is the wiring and the explicit-outcome contract.

### Cross-restart idempotency (#5): documented, not closed

The `real-lifecycle.ts` header carries a RESTART BOUNDARY note stating the `outcomeCache` and the Shopify ActionPorts' dedup are both in-memory, that within a live instance at-most-one-effect holds (proven by the replay test), and that across a restart only Razorpay's server-side key survives — so the Shopify legs could re-drive a second draft on a crash between draft and finalize. Persisting the idempotencyKey→effect correlation is explicitly deferred to the durable-resume milestone, matching the v1 recommendation to document rather than fix within this task's scope.
