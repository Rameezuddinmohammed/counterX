# Wire real Razorpay + Shopify connectors into the worker lifecycle (v1)

This task builds the last missing pieces to run one real checkout end to end: a fetch-based Razorpay HTTP client (the provider already spoke through `RazorpayHttpPort`, only a mock existed), env-gated connector factories for both providers, a boot-time selector that wires the real connectors when credentials are present and falls back to a deterministic in-process port otherwise, and a real `PaymentAuthorizationPort` that drives quote → draft → Razorpay order → CTP-signed payment evidence → finalize → mark-paid → order-query → reconcile → receipt. A creds-gated `verify:real` script exercises the exact worker wiring against the live test store. The credential gating (fail-loud in prod-like, mock-fallback in local/test), transport-layer idempotency and timeout handling, and the in-worker outcome cache are all solid and well-tested.

Watch for: (1) the Razorpay leg cannot actually produce the INDETERMINATE outcome the design requires — `RazorpayTestProvider.createInstruction` throws a generic `UNAVAILABLE` on any non-200, so the `real-http-client`'s carefully-built `reason:"timeout"` indeterminate marker is discarded and the two `razorpayResult.kind === "indeterminate"/"declined"` branches in `real-lifecycle.ts` are dead code (confirmed); (2) the CTP-signed payment envelope is dropped — only `evidence.reference` survives into the receipt, so the "signed receipt" is not actually signed evidence (confirmed); (3) reconciliation compares the payload's intended `amountMinor` against the Shopify order total (variant price × qty), which are independent inputs and will mismatch on almost every real run, routing successful payments to INDETERMINATE (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The credential-gating helper (`connector-env.ts`) is the policy spine: it resolves each provider's env vars, returns `null` to signal mock-fallback in local/test/development, and throws a variable-naming error in any other (prod-like) environment. Boot requires *both* provider credential sets before selecting the real port; a partial set in local/test silently falls back to deterministic, and a partial set in prod-like fails loud. Secrets are read from env only and never logged — verified across the helper, factories, HTTP client, receipt sink, and script.

The real Razorpay HTTP client is the strongest part of the change: Basic auth, the `X-Razorpay-Idempotency` header for retry-safety, a bounded `AbortController` timeout, and a deliberate design where transport failures return a synthetic `503` with a `reason` field distinguishing an indeterminate `timeout` from a hard `network` failure — rather than throwing. This is exactly the shape invariant #2 wants. The problem is downstream: `RazorpayTestProvider.createInstruction` only checks `status !== 200` and throws a generic `UNAVAILABLE` canonical error, so that `reason:"timeout"` signal never becomes an INDETERMINATE lifecycle outcome. It escapes the money seam as a thrown error and is reclassified by the worker loop as `handler.unexpected` (retryable) — not the typed INDETERMINATE path with a recorded receipt that the design and the (dead) code in `real-lifecycle.ts` promise.

The lifecycle wiring honors the explicit-outcome contract correctly for every *Shopify* leg (each `unwrapOutcome` maps `indeterminate` to an indeterminate result and never collapses to failed) and enforces at-most-one-external-effect within a process via a per-transaction outcome cache plus stable idempotency keys. The gaps are that idempotency across a process restart leans entirely on Razorpay's server-side key (the Shopify legs' in-memory idempotency store is lost on restart), and that "confirmed" is reconciled against the Shopify order total rather than the amount the payment was authorized for.

The end-to-end script cleanly reuses `selectPaymentAuthorizationPort` and the real handler instead of re-implementing the flow, skips gracefully without creds, and does best-effort cleanup — but the "final signed receipt" it prints is the internal state/reconciliation object, because the CTP envelope was already discarded upstream.

### Razorpay timeout can't become INDETERMINATE — dead branches in the money seam

The `real-http-client` was built to preserve the indeterminate/unavailable distinction the design demands. A fetch rejection or `AbortController` abort returns a synthetic response instead of throwing:

```ts
const failureBody: TransportFailureBody = {
  error: {
    code: "PROVIDER_UNAVAILABLE",
    reason: aborted ? "timeout" : "network",
    description: aborted ? "...outcome is indeterminate" : "...transport layer",
  },
};
return { status: TRANSPORT_UNAVAILABLE_STATUS, body: failureBody as unknown as T };
```

The unit tests assert both `reason:"timeout"` and `reason:"network"` are surfaced. But the provider that consumes this throws away the distinction:

```ts
// razorpay-provider.ts, createInstruction
if (response.status !== 200) {
  throw createCanonicalError({ code: "UNAVAILABLE", category: "unavailable",
    message: `Razorpay order creation failed with status ${response.status}` });
}
```

`createInstruction` only ever returns `action_required` (on 200) or throws. It never returns `kind: "indeterminate"` or `kind: "declined"`. So in `real-lifecycle.ts`:

```ts
if (razorpayResult.kind === "action_required") { razorpayOrderId = ...; }
else if (razorpayResult.kind === "indeterminate") { return indeterminate(...); }  // dead
else if (razorpayResult.kind === "declined")      { return declined(...); }       // dead
```

both non-`action_required` branches are unreachable. The real behavioral consequence: a Razorpay timeout after the request was sent — precisely the "possible external effect, unknown outcome" case invariant #2 says must be INDETERMINATE — is thrown as a generic `UNAVAILABLE` out of `authorizeAndCapture`. The worker loop's `classifyError` catches unknown errors as `handler.unexpected` retryable, so it doesn't hard-fail, but it also never transitions the state machine to INDETERMINATE and never records the indeterminate receipt that the payload-timeout and Shopify-timeout paths both produce. The Shopify legs get this right via `unwrapOutcome`; the Razorpay leg is the one place the explicit-outcome contract is not actually enforced. Fix by mapping the transport `503`/`reason` inside the provider (or catching the canonical `UNAVAILABLE` in the lifecycle and converting to `indeterminate("razorpay.order.indeterminate", ...)`), and add the missing test.

### The signed receipt isn't signed

`CounterTestPaymentProvider` produces genuine CTP-signed evidence and stashes the envelope where the port contract puts it:

```ts
// test-provider.ts #generateEvidence
const withData = envelope !== undefined
  ? { ...withConfirmed, providerData: { envelope } as Record<string, unknown> }
  : withConfirmed;
```

But the lifecycle only extracts the opaque reference:

```ts
function buildReference(paymentEvidence, razorpayOrderId, shopifyOrderId) {
  const parts = [`pay:${paymentEvidence.reference}`, `shopify_order:${shopifyOrderId}`];
  if (razorpayOrderId !== undefined) parts.push(`razorpay_order:${razorpayOrderId}`);
  return parts.join("|");
}
```

`providerData.envelope` is dropped. The outbox receipt (`main.ts` `createOutboxReceiptSink`) and the `verify:real` "FINAL signed receipt" step therefore carry only provider-reference strings and state/reconciliation — not the cryptographic evidence. FEAT-004's acceptance criterion asks for "the CTP-signed envelope / receipt object," and invariant #3 wants "confirmed" backed by typed provider evidence that is actually persisted. The reference-only receipt satisfies the letter (references, not secrets) but not the intent. Thread the envelope (or a typed evidence object) into `PaymentAuthorizationResult`/`TransactionReceipt` so the signed evidence is what gets recorded. Note that no secret leakage exists either way — this is about preserving evidence, not redaction.

### Reconciliation compares intended amount against the Shopify order total

The captured amount returned on success comes from the Shopify order query:

```ts
const providerAmountMinor = toMinorUnits(orderResult.totalPrice, request.currency);
const captured = Object.freeze({ status: "captured", capturedMinor: providerAmountMinor, ... });
```

and the handler reconciles it against `payload.amountMinor`:

```ts
reconciled: providerResult.capturedMinor === payload.amountMinor
```

The Shopify order total is the variant price times quantity, set by the store catalog. `payload.amountMinor` is the amount the transaction/Razorpay order was authorized for. These are independent inputs — the draft is built from `variantId + quantity`, not from `amountMinor`. Unless a caller happens to pass an `amountMinor` equal to the live variant price, every real run mismatches and the handler routes a fully-successful payment to INDETERMINATE + a `reconciliation.mismatch` retryable failure. The mock test passes only because the fixture sets both to 4999/"49.99". Either reconcile the provider-reported *payment* amount (Razorpay order amount / payment evidence) against intent, or derive the checkout amount from the resolved variant so the two are defined to agree.

### Idempotency: strong within a process, restart-dependent across the Shopify legs

The per-transaction `outcomeCache` plus using `request.idempotencyKey` verbatim for every effect gives a clean at-most-one-effect guarantee within a live port instance, and the replay test proves exactly one draft, one finalize, and one Razorpay order across two calls. Indeterminate outcomes are deliberately not cached so a later attempt can resolve them — correct. The limitation is durability: on a worker restart the `outcomeCache` and the Shopify actions' in-memory idempotency store are both gone, leaving only Razorpay's server-side `X-Razorpay-Idempotency` as a cross-restart guard. A crash between a successful draft and finalize would, on retry, create a second Shopify draft. The Shopify store being in-memory is pre-existing, but the worker wiring now depends on it for the "at most one external effect" claim, so the restart boundary should be documented (and is not exercised by the in-process replay test).

### Credential gating and secret hygiene

`connector-env.ts` cleanly isolates the environment policy: injected env bag (no global `process.env` reads, so tests need no mutation), empty/whitespace treated as absent, `isProdLike` defaulting unknown/absent envs to prod-like (fail-fast), and error messages that name missing variables without their values. `selectPaymentAuthorizationPort` requires both provider sets and fails loud in prod-like via the `require*` helpers before the loop starts. Secrets flow env → factory → HTTP client only; `redactAuthorization` is provided and the `real-http-client` never logs the header, and the receipt/outbox path carries references and amounts only — no credential, PAN, CVV, or UPI PIN reaches the DB, logs, or receipts (invariants #5/#6).
