# Backend Docker build via TypeScript project references (v1)

The Fly backend images were failing to compile because package `build` scripts ran `tsc -p tsconfig.json` and pnpm's parallel recursive scheduler could start a dependent's compile before a dependency had emitted its `dist/*.d.ts`, producing TS2307 in clean layers; the Dockerfile also built the whole workspace (all four Next consoles included) which exhausted the Fly builder, and prod builds compiled `*.test.ts` and hit TS7006. The fix converts every tsc-built package and app to TypeScript project references: each `tsconfig.json` gains a `references` array of its direct `@counter/*` dependencies, each gets a sibling `tsconfig.build.json` that excludes test files and references its dependencies' build variants, and each `build` script becomes `tsc -b tsconfig.build.json`, so a single `tsc -b` invocation compiles the whole closure in topological order. The Dockerfile now resolves the target package *name* and builds only `<name>...` (the app plus its workspace dependency closure), leaving the four Next consoles out of the backend image.

Watch for: a test-support source file in `apps/worker/src` is not matched by the exclude globs and still compiles into the worker's production `dist/` (confirmed - low severity, and strictly better than the prior build which shipped all test files); and the Dockerfile's package-name resolution silently degrades to building the entire workspace if `BUILD_TARGET` is ever empty (possible - all three fly configs set it, so not currently triggered).

**Verdict**: APPROVED

## High-level view

The references wiring is accurate across the board. Every one of the 30 tsc-built projects has a `references` array that exactly mirrors its direct `@counter/*` dependencies (verified by diffing declared deps against reference paths), and every `tsconfig.build.json` references its dependencies' `tsconfig.build.json` rather than their default configs, so the build graph and the type graph agree. The four Next consoles (`landing`, `merchant-console`, `operations-console`, `wallet-console`) keep `next build` and were correctly left without references.

The Docker gating strategy holds up empirically. Resolving the package name and filtering `<name>...` produces closures containing only the app and its transitive `@counter` dependencies - no `@counter/ui`, no consoles, no testkit - for all three backends, so the out-of-memory constraint is preserved by construction rather than by luck.

Excluding `*.test.ts` and `*.integration.test.ts` from the production build does not hide production-code type errors: prod sources still compile, and `typecheck` (`tsc -p tsconfig.json --noEmit`) and `test` still see the test files, so type regressions in tests remain caught in CI. The exclusion is a net improvement over the prior `tsc -p` build, which emitted every test file into `dist`. It is incomplete, though - test-support and fixture files that don't follow the `.test.ts` naming still land in prod output.

## Issues (2, non-blocking)

1. **Test-support leaks into prod dist** - `apps/worker/src/adversarial-test-support.ts` (and exported `fixtures.ts` / `mock-graphql-client.ts` in several packages) don't match the `*.test.ts` exclude globs, so they compile into production `dist`. Harmless to the build but ships test-only code; consider a naming/exclude convention (e.g. `*.testsupport.ts`) if a clean prod surface is wanted.
2. **Dockerfile name resolution fails open on empty BUILD_TARGET** - `require('./${BUILD_TARGET}/package.json')` resolves to the root `package.json` when the arg is empty, and `<root-name>...` would build the whole workspace (reintroducing the OOM). All three fly configs pass the arg, so it's latent; a guard that fails the build on an empty/invalid `BUILD_TARGET` would harden it.

## Notes

- References mirror the real dependency graph: exact match for all 30 tsc-built projects; build variants reference dependencies' build variants; leaf packages carry empty references. Next consoles depend on `@counter/ui` (resolved from source) and intentionally have no references.
- Docker closures verified: worker, agent-runtime, control-plane-api each pull only the app + transitive @counter deps, no ui/testkit/consoles. OOM enforced structurally.
- Test exclusion narrows prod output without hiding prod type errors (typecheck + vitest unchanged and still see tests).

**Verdict**: APPROVED
